Case study 01 Enterprise OTT operator console

Designing Channel Creation from a one line requirement

The request was a single sentence. Over several months and more than twelve releases, it became a 150 field system that operators use to create, update and delete TV channels. I designed it together with Solution Architecture and Engineering.

My roleUX designer, UX architect and UI designer
TeamSolution Architect, Solution Developer, Senior Developer
ScopeCreate, update, delete, recordings and job tracking
TimelineSeveral months, 12+ releases
ToolsFigma, FigJam, Jira, Confluence

01 Overview

One sentence of brief. 150 fields of real work.

Channel Creation started with one line from the business: "We need to build channel creation." There was no spec, no field list and no earlier design to start from. Operators simply needed a way to launch a TV channel from inside the console.

Over the next few months I worked closely with the Solution Architect, the Solution Developer and a Senior Developer to find and name every field a channel needs. New areas such as Bouquet Management and Catalogue linking appeared along the way. My job was to turn that growing list into something an operator could fill in without losing track.

What I owned
  • Field grouping and information architecture
  • The five step form, validation rules and the preview step
  • Listing, save safety and job tracking screens
  • The safe deletion flow and the recordings entry point
  • All UI, prototypes and developer handoff
What I did with the team
  • Finding and naming every field, in working sessions with Architecture and Engineering
  • Deciding which fields depend on others
  • Checking what the backend could support in each release

02 The brief

"We need channel creation." That was all we had.

Nobody knew how many languages, delivery types or security rules a channel would need. On the first day, three questions had no answer.

Open question 1

Which fields matter?

Metadata, delivery, security, monetisation and advertising were all still unlisted.

Open question 2

Which fields depend on others?

Some values only make sense after another field is set, and nobody had written that logic down.

Open question 3

Where do sub features fit?

Bouquet Management and Catalogue linking only came up once we mapped what a channel needs to go live.

03 Discovery

Finding 150 fields, one working session at a time.

I didn't do this alone. The Solution Architect, the Solution Developer and the Senior Developer sat with me for session after session. Each of them looked at the problem differently, and we only trusted the field list once all three agreed with it.

Solution Architect

System rules

Explained the entitlement and delivery rules every field had to respect.

Solution Developer

Data model

Mapped the backend data models to the fields the form needed to capture.

Senior Developer

Feasibility

Checked what could be built and flagged dependent fields early.

Areas that came up during discovery

Bouquet managementCatalogue linkingDelivery configurationSecurity and DRMEnablersAdvertisement
150 fields can't sit in one form. The problem needed structure first.How I framed it for the team

Long forms usually fail in the same ways. People lose their place, errors pile up at the end, and people give up once they have to scroll instead of scan.

04 Information architecture

Every field got a home, for a reason.

I placed each field in the section it belonged to and ordered the sections the way operators think about a channel. First what the channel is, then how it is delivered, how it is protected, what features it has and how it earns money.

05 Key decisions

Six decisions that made 150 fields manageable.

Decision 1

Steps instead of one long form

Each field lives in exactly one step, so operators finish one focused section at a time.

Decision 2

Next stays disabled until the step is valid

Operators can only move on when every required field is filled, so errors don't pile up at the end.

Decision 3

Preview before submit

A channel affects real viewers, so the last step is always a full read only review.

Decision 4

Confirm before create

Submitting from Preview asks once more, so nobody creates a channel by accident.

Decision 5

Same pattern for update

Updating a channel uses the same steps and preview, so there is nothing new to learn.

Decision 6

Show only what is needed

The saved channel page opens General and keeps the other sections collapsed.

07 Final design: creation

Start simple. Add detail step by step.

The first screen is deliberately quiet, with one clear action. Operators choose the channel type first, so the form only shows the fields that apply to that type.

  1. Progress is always visibleThe tracker at the top shows the current step and what is left.
  2. Fetch MetadataEntering a Channel ID can fill in known details automatically.
  3. Language gridSix language fields side by side with character counts.
  4. Next buttonStays disabled until the step is complete.
08 Final design: listing and saving

One table for every distribution type.

Channels are split into Commercial TV, Commercial Radio, FAST O&O, FAST 3PP and App Launch Point. Each type gets its own tab, and the Broadcast and OTT columns are grouped so operators can see what is switched on at a glance.

  1. Add ChannelTop right, in the same place as every other list in the console.
  2. A tab per typeEach type gets its own table instead of one crowded list.
  3. Toggles in the rowEnable, watermark and DRM can be changed without opening the channel.
  4. Row actionsEdit, view, delete and save sit on each row.

Quick edits on a table of 400 channels are where mistakes happen. So I added two safeguards. Operators can't lose unsaved changes by navigating away, and every save asks for confirmation and names the exact channel being changed.

09 Final design: job tracking

Creating a channel takes time, so the screen shows it.

Every create, update and delete starts a backend job that can take a while. Instead of a spinner, each job gets a status that names its current stage: Merging, Transforming, Matching or Publishing.

  1. Instant confirmationA message confirms the job has started before the page reloads.
  2. Named stagesOperators can see exactly where each job is.
  3. Start and end timesSupport teams can answer "when did this go live?"
  4. Failures link to detailsA Details link opens the reason right there.
10 Update flow

Same steps, with one extra job for Preview.

Updating a channel uses the same steps as creating one. The only difference is in Preview. It highlights the fields that changed since the last save, using the same colours as the audit comparison I designed separately.

11 Safe deletion

A channel with millions of viewers needs a careful delete.

If a channel was still switched on while being deleted, any viewer could start a recording at that moment. That recording would then point to a channel that no longer exists. So I designed deletion as a short sequence of checks instead of one click.

Check 1

Disable the channel first

Turning off Broadcast and OTT stops new recordings from starting.

Check 2

Remove recordings next

Recordings must be deleted first so no data is left without a channel.

12 Channel page

150 fields saved, but never all on screen at once.

The saved channel page follows the same structure as the form. General Details is open by default and Delivery, Security, Advertisement and Videos stay collapsed. Recordings sits in the header, and Version History was later added next to it without changing the navigation.

14 Learnings

What this project taught me.

Lesson 1

Discovery is design work

Naming 150 fields with Architecture and Engineering was part of the UX. I couldn't design the form until we knew the scope.

Lesson 2

Grouping matters more than count

Once the fields were grouped well, the number of fields stopped being the problem.

Lesson 3

Plan for change

Treating create, update, delete and recordings as one pattern made every new requirement easier to add.

Lesson 4

Design the edge cases as flows

The disable before delete rule became a proper flow from the start, not a patch later.

When the brief is one line, part of the job is designing the scope itself.
