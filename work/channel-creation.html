Case study 02 Enterprise OTT operator console · Shipped

Designing Channel Creation from a one line brief

The request was a single sentence. Working with Solution Architecture and Engineering, I turned it into a five step system with about 150 fields that operators use to create, update and delete TV channels.

RoleUX and UI designer, UX architect
TeamSolution Architect, 2 developers
TimelineJan 2025 – first release Jun 2025
StatusShipped, still extended
Reading timeAbout 6 min

NoteClient branding has been removed from all screens and the data shown is placeholder data.

Project at a glance

Problem
The brief was one sentence: "We need to build channel creation." No spec, no field list. A channel turned out to need about 150 fields, and a mistake in any of them reaches viewers.
My contribution
UX architect and UI designer: found and grouped the fields with Architecture and Engineering, then designed the step flow, preview, listing, safe deletion and job tracking, through to handoff.
Key decision
Split the fields into five steps chosen by channel type, with a read only preview before anything is created.
Result
First release in June 2025, then 12+ releases built on the same pattern. Evidence is release history; this console has no product analytics.

01 Context

One sentence of brief. About 150 fields of real work.

Channel Creation started with one line from the business: "We need to build channel creation." Nobody yet knew how many languages, delivery types or security rules a channel would need.

My first job was not screens. It was helping the team find out what a channel actually is.

Open question

Which fields matter?

Metadata, delivery, security, monetisation and advertising were all unlisted.

Open question

Which fields depend on others?

Some values only make sense after another is set, and that logic was not written down.

Open question

Where do sub features fit?

Bouquet Management and Catalogue linking only appeared once we mapped what a channel needs to go live.

03 Decisions

The choices that made 150 fields workable, and what they cost.

Key decisions and trade offs
DecisionUsual alternativeWhy I chose itWhat it costs
Steps chosen by channel typeOne long form, or tabsEach field lives in one focused step, and the type hides fields that don't applyMore clicks to reach a field in a later step
Next is enabled only when the step is completeValidate everything on submitErrors can't pile up across five steps and appear all at once at the endA disabled button doesn't explain what is missing on its own
Read only preview before createSubmit straight from the last stepA channel reaches real viewers, so the last step is a full reviewOne extra step on every create and update
Confirm before create and on saveSave without askingThe confirmation names the exact channel, which matters in a table of hundredsFriction on frequent, low risk edits
Same steps for updateA separate edit screenNothing new to learn, and the preview can show what changedUpdate inherits every limit of the create flow
Future proposal
Reflection: two trade offs to revisit

A disabled Next should list the required fields still empty in that step. For low risk inline toggles, an undo could replace the confirmation dialog, keeping confirmation for changes that affect live delivery. Neither is shipped.

04 Solution

Five steps, chosen by channel type.

05 Listing and saving

Fast edits, made safe.

Each distribution type gets its own tab. Broadcast and OTT columns are grouped, and enable, watermark and DRM can be toggled in the row.

06 Job tracking

Backend jobs, made visible.

Every create, update and delete starts a backend job. Instead of a spinner, each job shows its current stage: Merging, Transforming, Matching or Publishing, with start and end times so support can answer "when did this go live?"

07 Update and delete

Same steps for update. Checks before delete.

Updating uses the same steps as creating. In Preview, the fields that changed since the last save are highlighted with the same colours as the audit comparison.

Illustrative example

Deleting a channel that is still live could leave a viewer's recording pointing at a channel that no longer exists. So delete is a short sequence of checks instead of one click.

Delete flow

  1. Delete
  2. Still enabled? Blocked
  3. Disable Broadcast and OTT
  4. Recordings exist? Blocked
  5. Delete recordings
  6. Delete allowed

08 Scope and reflection

What the numbers mean, and what they don't.

Lesson

Discovery is design work

Naming the fields with Architecture and Engineering was part of the UX. The form couldn't be designed until the scope was known.

Lesson

Grouping matters more than count

Once the fields were grouped well, their number stopped being the problem.

Lesson

Design edge cases as flows

Disable before delete became a proper flow from the start, not a patch later.
